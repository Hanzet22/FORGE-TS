# Phase 31 — PRoot RootFS Provisioning Design

Status: design baseline for P0.8; no distro image is downloaded or installed by this document.

## Scope

Provide separate ARM64 root filesystems for Debian, Ubuntu, and Alpine inside the existing app-private workspaces:

- `filesDir/forge-runtime/proot/debian/rootfs/`
- `filesDir/forge-runtime/proot/ubuntu/rootfs/`
- `filesDir/forge-runtime/proot/alpine/rootfs/`

Do not bundle rootfs archives in the APK. Do not change Supabase, Redis, the existing runtime registry, or the PRoot native engine.

## Official source policy

Only use upstream distribution sources and their published integrity metadata.

| Distribution | Initial source family | Candidate artifact | Integrity source |
|---|---|---|---|
| Alpine | https://alpinelinux.org/downloads/ | Official aarch64 Mini Root Filesystem `alpine-minirootfs-<version>-aarch64.tar.gz` | Official SHA256 and GPG links published with the release |
| Debian | https://docker.debian.net/ | Official Debian arm64 rootfs tarball generated by debuerreotype; prefer a dated stable tag over a moving tag | Per-artifact SHA256 and published build/snapshot metadata; pin the exact artifact and digest |
| Ubuntu | https://partner-images.canonical.com/oci/noble/current/ | Canonical OCI arm64 root archive `ubuntu-noble-oci-arm64-root.tar.gz` | Matching `SHA256SUMS` and `SHA256SUMS.gpg`; verify signature before trusting the checksum list |

Related official references:
- Alpine download and verification guidance: https://wiki.alpinelinux.org/wiki/Installation
- Ubuntu OCI registry documentation: https://ubuntu.com/docs/oci-registries/
- Ubuntu public image metadata and signature format: https://ubuntu.com/docs/public-images/
- Debian official image reproducibility and rootfs checksums: https://docker.debian.net/

The catalog must store an immutable version, architecture, exact archive URL, expected SHA-256, checksum/signature URL, and source metadata before an installation is offered. A moving `latest` URL is discovery metadata only; it is not an install identity. Do not hardcode a checksum copied from a search snippet. Resolve and verify it from the official source at catalog refresh time, then pin it in the catalog response used by that install.

## Provisioning transaction

1. Create an isolated staging directory under the selected distro workspace, never directly in `rootfs/`.
2. Download over HTTPS with bounded redirects, a configurable archive-size ceiling, cancellation, and a temporary `.part` file.
3. Verify the upstream signature where provided, then verify the archive SHA-256 against the authenticated checksum metadata.
4. Inspect archive entries before extraction. Reject absolute paths, parent traversal, device nodes, sockets, unsafe links, duplicate path tricks, and entries whose resolved targets escape staging.
5. Enforce limits for entry count, expanded bytes, path length, nesting depth, and per-file size.
6. Extract into staging. Do not execute scripts from the archive during installation.
7. Verify the expected ARM64 userland and required paths, including readable `/bin/sh`, `/etc`, and a coherent `/usr` tree. Verify ELF machine architecture for key executables where practical.
8. Write a local install manifest containing distro/version/architecture, source URL, archive digest, verification result, install timestamp, and app catalog revision.
9. Atomically promote staging to `rootfs/` only after every check succeeds. Preserve the previous valid rootfs until promotion succeeds.
10. Only then transition the instance to `READY`. A prepared workspace or downloaded archive alone is never READY.

## Archive format decision

- Alpine Mini RootFS and Canonical Ubuntu OCI root archives are gzip-compressed tar archives and are suitable initial candidates for a bounded in-app extractor.
- Debian's published rootfs tarballs are commonly `.tar.xz`. Do not silently pass XZ data to a gzip-only extractor. Either implement and review an XZ decoder path or select a verified official OCI layer flow and correctly apply OCI whiteouts. This decision is a hard gate before Debian download UI is enabled.
- OCI layer application must preserve layer order and whiteout semantics. A single layer extraction is not equivalent to a complete image rootfs.

## Security constraints

- Archive contents are untrusted input even when the archive digest is valid: the digest authenticates bytes, not safe filesystem semantics.
- Use descriptor-relative extraction / no-follow semantics where available to reduce symlink and TOCTOU escapes. Never trust a path after checking it once and then reopening it by name.
- Never extract as privileged Android root; the app does not require root.
- Do not create device nodes or mount filesystems.
- Never run package scripts during installation.
- Avoid redirects that downgrade HTTPS or change to an untrusted origin.
- Keep downloads and extraction cancellable, report progress, and clean staging on failure.
- Do not delete user data or a previous working rootfs during an update failure.
- PRoot shares the Android host kernel and is not VM-grade isolation. Clearly label this in the UI.

## Lifecycle integration

- `NOT_INSTALLED`: no verified rootfs.
- `STARTING` / install progress: provisioning operation in progress; do not expose as runtime STARTING unless a process is launched.
- `READY`: native engine, loader, and verified rootfs are present; this is install readiness, not proof that a guest process has run.
- `RUNNING`: only after adapter confirms a live process.
- `FAILED`: install or launch failed; preserve diagnostics and safe recovery path.
- `RECOVERY_REQUIRED`: interrupted promotion or uncertain filesystem state; inspect manifest and staging before reuse.

## Implementation sequence

1. Add a typed, immutable rootfs catalog model with explicit source and verification metadata.
2. Add download-to-staging and SHA-256 verification.
3. Add safe gzip-tar extraction with strict entry limits.
4. Enable Alpine and Ubuntu only after the extraction path supports their archive format and integrity metadata.
5. Resolve Debian XZ / OCI-layer strategy separately; do not ship a partial or silently incorrect Debian installer.
6. Wire install state and manifest into the existing PRoot instance registry.
7. Add a concise install status UI and recovery messaging.
